# Application communication needs

## Purpose and scope

This document describes the communication needed by the Gateway, browser workspaces, paired Agent, desktop manager and Odoo addon. It identifies external dependencies and places where a user or operator can select an external destination. It addresses the documentation subject of ASVS V13.1.1; it does not certify a deployment or replace exact-runtime acceptance.

Repository-relative source references describe implemented behavior; references prefixed with `github.com/grandcat/zeroconf@v1.0.0/` identify that pinned Go dependency, not first-party repository files. Deployment operators must resolve configurable destinations into a maintained environment-specific inventory and verify it against the selected runtime. Example configuration values are not production addresses. Keep credentials, receipt content and private authentication material out of the published inventory.

Documenting the application communication requirements and verifying a selected deployment are separate tasks. A deployment hostname, CA, collector identity or physical interface resolves a documented configurable connection; an unexecuted packet capture or Windows test does not by itself mean that connection is undocumented. The acceptance procedures below validate the chosen configuration and runtime without replacing the application-level inventory.

The following matrix consolidates these component descriptions with their source-level communication boundaries. Deployment-specific values remain explicit configuration requirements rather than inferred addresses.

### Pinned mDNS socket behavior

In zeroconf v1.0.0, `connection.go:17–25,38–39,68–69` binds UDP listeners using `224.0.0.0:5353` and `[ff02::]:5353`; the distinct query/announcement multicast destinations are `224.0.0.251:5353` and `[ff02::fb]:5353` (`connection.go:12–35`). These bind literals describe dependency code, not a claim about successful Windows socket behavior. Group membership is attempted per selected interface, and the family fails if no interface can join (`connection.go:48–63,79–94`). Queries use an explicit interface index for each selected interface (`client.go:435–453`). Default selection calls `net.Interfaces()` and keeps interfaces with both `FlagUp` and `FlagMulticast`; it does not filter by adapter name (`connection.go:99–114`). The Agent supplies `SelectIPTraffic` only and launches IPv4/IPv6 separately (`agent/internal/printer/ipp_discovery.go:245–275`). A target host’s actual adapter flags, multicast routing, firewall and family-specific success remain deployment observations.

## Deployment information to maintain

1. **Deployment-resolved identities:** maintain a manifest of selected public Gateway/Odoo FQDNs, DB/proxy/collector locations, source networks, allowed egress, trust stores and owning service accounts. Preserve these as sanitized configuration metadata, never secret values. Source defaults cannot establish the deployed topology.
2. **Conditional provider flows:** explicitly distinguish HIBP password-screening dependency, transactional email, Stripe server API/webhook and browser navigation. Provider outage and redirect behavior differ; do not copy the Odoo/Agent “no proxy/no redirects” description onto all fetch clients. In particular `src/lib/email.ts:49–54` and `src/lib/stripe.ts:74–79` do not set the explicit redirect refusal used by HIBP.
3. **User-controlled locations:** document Tauri's candidate Gateway origin, Agent saved Gateway origin, Odoo's editable URL plus deployment allowlist, and printer IP/URI/queue selection. Pairing/trust confirmation and printer ownership are distinct from syntactic URL/address validation. Mail recipient input is another externally delivered destination, with a fixed HTTP provider.
4. **LAN and OS dependencies:** apply the documented discovery families, multicast addresses/ports and interface-selection policy separately from print execution. Record which interfaces satisfy the policy on the selected host, and enumerate configured Windows queue/driver destinations. USB, spooler/GDI, WebView2 and upstream Odoo integrations are declared configurable dependency classes; their selected implementations require deployment inventory. Printer-port reachability does not establish device identity, IPPS downgrade permission or safe replay.
5. **Provisioning versus steady-state traffic:** WebView2 download/bootstrap/update, certificate issuance/renewal, DNS, Odoo's upstream integrations and any dependency telemetry need a selected-runtime inventory. Package registries, source downloads, CI services and signing/timestamp infrastructure belong to the build/provisioning profile, not an implied always-on runtime allowlist. The application clients listed here do not configure a vendor telemetry receiver; this scoped inventory does not establish the absence of dependency or OS traffic.

## Deployment review and acceptance

Run these procedures on the selected environments and retain their results. The source inventory itself is not evidence that a connection or device has been exercised:

1. Resolve each configured matrix row into a sanitized manifest: initiating service/account, destination hostname/IP, scheme/port, purpose/data class, source network, CA/proxy/DNS policy, conditional feature and evidence owner. Use `docker compose config --no-interpolate` for template review; inspect live secret-backed configuration privately and publish only the selected non-sensitive fields.
2. On a disposable exact release deployment, perform the normal customer/manager/platform password login/confirmation/session flows, HIBP-screened password setup, test-provider email and Stripe checkout/webhook, Odoo inventory/print-status requests, and authorized metrics scrape. Record browser network origins and process-attributed host egress metadata, with request bodies, cookies, authorization headers, email links and receipt content excluded. Confirm observed destinations match the declared manifest and exercise provider/DNS/proxy/CA refusal paths.
3. On the exact Windows/CGO/installer environment, execute `docs/WINDOWS_RELEASE_ACCEPTANCE.md` after recording the selected OS/runner image, native Go/CGO compiler identity and hash, Rust MSVC toolchain, Node/package lock, installer hash and WebView2 version. Missing exact compiler/runtime provenance prevents exact-build verification. Capture WebView2 bootstrap/renewal behavior, Agent HTTPS/WSS, Tauri probe behavior, selected discovery interfaces and real printer/driver traffic. Linux/native/cross-compilation evidence does not execute these Windows sockets/drivers or produce physical print acceptance.
4. Review each user-supplied destination policy against the selected deployment, including disallowed origins/metadata addresses, redirect responses, DNS changes, proxy inheritance and certificate failures. Use synthetic authorized endpoints and the existing regression/acceptance procedures; do not send real credentials to candidate sinks. Then bind the completed manifest and observations to exact source, runtime, installer and configuration hashes.
5. Preserve the physical-outcome rule during any outage/dispatch capture: after bytes may have reached a printer, an unknown outcome remains reconciliation-required; there is **no automatic reprint or alternate-printer failover** (`docs/WINDOWS_RELEASE_ACCEPTANCE.md:178,221`; `README.md:39–41`). A network retry must not bypass that physical-outcome boundary.

Keep the application inventory synchronized when a destination, provider, protocol, proxy, runtime dependency or user-configurable connection feature changes. Review any newly introduced flow as a documentation change. Separately record the selected deployment configuration and repeat affected runtime observations; keep documentation review and executable acceptance results distinct.
