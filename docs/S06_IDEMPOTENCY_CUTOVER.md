# S06-006 — Odoo installation namespace, historical reconciliation, and safe cutover

**Release status:** implementation staged; do not approve production without native Gateway/PostgreSQL/Odoo acceptance and a verified restore rehearsal. Migration `0085_odoo_installation_idempotency` is additive and makes **no changes** to historical `print_jobs`, `print_job_receipts`, or existing Odoo outbox identities. No physical output is implied by an HTTP/Agent/spooler acknowledgment.

## Identity contract and prerequisites

The legacy wire key (version 1) remains `SHA256("odoo:<odoo-local-company-id>:<durable-operation-id>")`. This exact derivation is frozen for all pre-upgrade Odoo jobs, including stale `unknown` and already-completed jobs. Even a credential change or database restoration must not re-key such records.

For **new jobs only**, the Gateway issues a random UUIDv4 installation ID and a separate random 256-bit enrollment proof to each *independent Odoo installation*. The proof is displayed **once**, stored only as a SHA256 hash in Gateway, and provisioned outside the Odoo database. A v2 wire key is the SHA256 of compact JSON `["yaseir-odoo-v2",<enrolled UUIDv4>,<company ID as decimal string>,<durable operation ID>]`. Proof is sent in `X-Yaseir-Odoo-Proof`; the registration and current API key are checked under Gateway transaction locks. The Odoo outbox stores only the version, original wire key, and installation ID.

Do **not** reuse one Gateway API key across independent installations: unique credential association intentionally enforces one owner. A database clone with a copied external secret, same key, and same installation ID is cryptographically indistinguishable from the original; isolate its runtime and explicitly re-enroll before enabling printing. A restore may preserve identity only after independently confirming that the previous runtime is retired. Never copy the external proof to an independent running clone.

## Operator runbook (maintenance window, non-destructive)

1. Backup and restore-test the PostgreSQL Gateway database and each Odoo database, including lifetime receipts, then record hashes and the exact release revision. Preserve external enrollment secrets in independently secured secret management. Stop **new Odoo printing** for the affected Gateway tenant during cutover; do not delete queued, `unknown`, or ambiguous operations. Pause creation at the Odoo source and wait for in-flight Gateway jobs to drain. Separate unresolved printing outcomes for human verification.
2. Deploy the **compatible Gateway first**, run `npm run db:migrate` on the intended local/staging database and verify migration journal `0085` and registry tables. **Do not set strict mode yet.** Migrate the Odoo addon using the supported native Odoo 19 module-upgrade procedure. Verify all Odoo outbox records preserve their original v1 hash on upgrade.
3. For *each independently managed Odoo database*, generate a distinct enabled Odoo Gateway API key, then authenticate as a workspace manager with `integrations.manage` and POST `{"name":"Installation description","apiKeyId":"<existing active Odoo API-key row ID>"}` to `/api/odoo/installations`. Store the returned `installationId` in Odoo Gateway configuration; store its one-time `installationProof` in **external** secrets, never the database. For a multi-database Odoo process use `YASEIR_ODOO_INSTALLATION_PROOFS` containing a JSON UUID→proof map, with restricted file/process access. A single-instance process may use `YASEIR_ODOO_INSTALLATION_PROOF`.
4. Audit the Odoo durable outbox, `unknown` records, prior Agent acknowledgments, Gateway `print_jobs`, and payload-free lifetime `print_job_receipts`. The manager can GET `/api/odoo/installations/resolutions?installationId=<uuid>&sourceCompanyId=<decimal>&sourceOperationId=<id>`. A matching legacy fingerprint is **not proof** of installation ownership or paper output. Where a v2 business intent's legacy key already exists, explicitly approve **`reuse`** only if the old record is the *same* business intent, or **`distinct`** only if the old record demonstrably belongs to another independent installation. POST to `/api/odoo/installations/resolutions` with `installationId`, `sourceCompanyId`, `sourceOperationId`, `disposition`, the *observed* `expectedLegacyJobId` and `expectedLegacyFingerprint`, and `operatorAttestation: "HISTORY_AND_PHYSICAL_OUTCOME_REVIEWED"`. Every approval is audit-logged. `reuse` immediately publishes a durable v2→original receipt association: no new job, no quota debit, no new physical command.
5. Configure v2 on the **enrolled installation only** (Odoo Gateway configuration `idempotency_v2_enabled`). This changes only *subsequently created* outbox rows. Any v2 POST before the Gateway strict switch is rejected as `CUTOVER_NOT_ACTIVE` and remains parked with its immutable v2 identity. Do not retry with a legacy key or rename existing rows.
6. As a manager, POST `{"mode":"strict_v2","verifiedExternalOutboxes":true,"verifiedReceiptBackup":true,"verifiedAllInstallationsEnrolled":true}` to `/api/odoo/installations/cutover`. Gateway checks an enrolled installation and zero outstanding `queued`/`claimed`/`printing` Odoo Gateway jobs under the tenant lock and switches the tenant **one-way** to strict v2. New legacy Odoo POSTs fail with `UPGRADE_REQUIRED`; historical v1 GET lookups remain supported. An older Gateway lacking this contract must reject v2, never fall back silently to a new v1 POST.
7. Run acceptance in a test tenant: identical local company/operation IDs across two independent Odoo databases, matching and differing print bytes, clone without secret, credential rotation, strict-mode legacy rejection, pending/unknown/stale v1 receipts, operator `reuse`/`distinct`, delayed Agent acknowledgments, concurrent duplicate submissions, status GET by original job ID, and restore with old receipts intact. Verify **one** admitted job for a given business intent, exactly one quota debit for new admission, no quota debit for `reuse`, and never infer physical paper delivery from Agent/spooler acknowledgments. Do not connect unknown printer languages or send test jobs to physical devices without capability verification.

## Gateway behavior and operations

- `GET /api/odoo/installations` returns enrolled IDs/metadata but **never proofs**.
- `POST /api/odoo/keys/<id>/rotate` creates a new key and transactionally carries forward the installation association. The original key remains read-only during its documented grace, then unusable; credentials never confer access to another installation.
- v2 POST supplies the exact `idempotencyKey`, `idempotencyVersion: 2`, `installationId`, `sourceCompanyId`, `sourceOperationId` in the JSON body and `X-Yaseir-Odoo-Proof` in the request header. The status GET also supplies `X-Yaseir-Odoo-Idempotency-Version: 2` and `X-Yaseir-Odoo-Installation` plus the proof header. POST/GET authenticate against live key, enrolled installation and hashed proof.
- `RECONCILIATION_REQUIRED` (409) means **do not create a new print**: human reconciliation is necessary. `INSTALLATION_NOT_ENROLLED` (403) means external proof/credential/installation check failed; no submission accepted. `CUTOVER_NOT_ACTIVE` (409) means v2 admission has not yet been enabled for this tenant. `UPGRADE_REQUIRED` (409) blocks legacy new POST after strict switch; historic GET remains available. Status-by-v2-key cannot return another installation's job.
- If a live job and its retained receipt both disappear, v2 reuse fails closed; loss of immutable history requires a separate recovery process with physically verified outcomes. Never reset `odoo_v2_operations` or `odoo_legacy_resolutions` and retry with a new identity.

## Rollback and unrecoverable conditions

Rollback **application binaries** only to a release that understands registered v2 identity, or isolate the tenant and disable Odoo printing. Do not revert the Gateway to legacy admission after v2 jobs exist, rewrite hashed history, drop migration `0085`, or regenerate a new installation identity automatically. Restore matched Gateway/Odoo backups, verify lifetime receipts and locked identities, then allow only the old already-accepted operations to reconcile. Keep fresh new print admission stopped until a manager reviews the migration and resumes strict v2.

This document is a procedure, **not evidence** that native Odoo/PostgreSQL, Stripe, Windows, or physical-printer release gates passed. Record actual executed results in the final test matrix.
