# V3 password authentication and session policy

V3 authenticates every human role with an email address and the account's exact password. A verified account receives its scoped access/refresh session and proceeds to the relevant dashboard. An account with several workspaces chooses its destination using a one-use signed chooser; that selection does not repeat password verification or create a later verification timestamp. Human session authentication is single-factor. Verified email at account setup does not make later password-only sign-in a combined-authentication ceremony.

## Entry points and authority

| Consumer | Login and destination | Required live authority |
| --- | --- | --- |
| Workspace user, including `owner`, `admin`, `operator`, `viewer`, `integration_admin`, `billing_admin` | `/login`, `POST /api/auth/login`, then `/dashboard` or an allowed same-origin workspace return path | Verified email, correct password, active selected tenant and current exact membership role |
| Database-backed manager client | `POST /api/auth/manager/login` | The same verified account/password/membership checks; manager session kind does not add permissions |
| Platform administrator | `/platform/login`, `POST /api/platform/auth/login`, then `/platform/dashboard` | Verified email and current `users.is_platform_owner`; workspace owner/admin membership cannot confer platform authority |
| Development/test environment manager | Explicitly configured compatibility path at the manager endpoint | Actual configured password, username and tenant snapshot; forbidden in production |
| Paired Agent, desktop bridge and Odoo installation | Existing machine credential endpoints | Separate Agent/tenant or API-key/installation authority; no human login bypass or platform role |

The schema has one Platform Owner flag and an at-most-one-owner constraint. “Platform administrator” in the UI names that authority; it is not a second unimplemented platform role. The six workspace roles and operation permissions remain in `src/lib/authorization.ts` and [SECURITY_AUTHORIZATION.md](SECURITY_AUTHORIZATION.md).

The implementation paths are `src/app/api/auth/login/route.ts`, `src/app/api/auth/manager/login/route.ts`, `src/app/api/platform/auth/login/route.ts`, `src/lib/customer-auth.ts`, `src/lib/manager-auth.ts`, `src/lib/platform-auth.ts` and `src/lib/session-tokens.ts`. Password verification produces an internal credential snapshot. Session issuance rechecks it under the current account lock; the snapshot cannot be supplied through request JSON and is not placed in a JWT or public response. Failed or unverified sign-in cannot mint a session. Unknown accounts perform password work before receiving the same invalid-credential response; this is a mitigation, not proof of indistinguishable timing across every deployed path.

## Passwords and mailbox recovery

New passwords must contain at least 12 Unicode code points and at most 4096 UTF-16 code units. The selected string is not trimmed or normalized. Login and legacy credential rehashing retain the existing 1–4096-code-unit verification policy, so an already valid password is not rejected by the new-password minimum. Spaces and letter case are significant. There are no composition requirements or periodic mandatory password changes. The account KDF remains salted Argon2id using the existing implementation parameters; existing supported scrypt credentials are handled by their established compatibility path. Common/contextual and compromised-password screening remains at registration, reset and bootstrap. Screening failures refuse a new password; they do not disable existing-password sign-in. See `src/lib/password.ts` and [PASSWORD_SCREENING.md](../security/PASSWORD_SCREENING.md).

Email verification, reset and initial mailbox-owner password setup retain CSPRNG-generated 32-byte tokens, hash-only storage, transactional single use and a maximum ten-minute lifetime measured by PostgreSQL. Both lookup and consumption reject future creation timestamps, expired stored deadlines and age at or above ten minutes. A shorter stored deadline wins. The existing invitation offer lifetime is separate from its mailbox proof. Mail delivery delay cannot extend authority. Reset revokes the user's session families and compares current state under lock; invitation acceptance binds the exact recipient and role. Existing-session invitation acceptance inherits source proof and the earliest deadline. See `src/lib/email-auth-token-policy.ts`, `src/app/api/auth/reset-password/route.ts`, `src/app/api/auth/verify-email/route.ts` and `src/app/api/team/invitations/accept/route.ts`.

Registration, forgot-password and resend-verification delivery run in Next's tracked post-response lifecycle after the relevant token transaction commits. The generic accepted response does not wait for an account-dependent mail-provider call. Delivery failures remain logged, and the custom server drains accepted callbacks on graceful shutdown. This is not a durable outbox: an abrupt crash or provider outage can still require resend-verification or another rate-limited reset request. The original ten-minute token deadline is never extended by delivery delay. Resend validates an invitation continuation before looking up the account so that an invalid invitation cannot expose account state through its response status. Database work can still differ between account states; these controls are not a proof of indistinguishable timing under every deployment condition.

Mailbox recovery remains a meaningful trust boundary. Control of the mailbox can enable an attacker to replace the password. There is no claim that email delivery, mailbox protection or provider account recovery has been verified merely because local token tests pass.

## Attempt reservation and malicious lockout

`src/lib/auth-rate-limit.ts` uses shared PostgreSQL reservations, so adding Gateway instances does not multiply account limits. Account identifiers use the established normalized bounded key. A trusted, sanitized proxy supplies a separate source-IP bucket. Without a trusted source address, the implementation skips the IP bucket instead of creating one global lock that an anonymous attacker could use to block every account; the account limit remains. Production must use the configured trusted-proxy boundary and should alert on `auth.rate_limit.untrusted_proxy`.

Account thresholds remain 5/10/15/20 reserved attempts; source-IP thresholds are 20/30/40/50. The progressive locks are 30 seconds, 5 minutes, 15 minutes and at most 60 minutes, with the existing 15-minute reservation window. A request arriving during an active lock is refused without extending that lock or increasing its attempt counter. Expired windows reset on the next reservation, and successful authentication clears the account success bucket. The limiter does not permanently disable an account. A distributed attacker can nevertheless repeatedly target an account after each lock expires; that availability risk requires traffic filtering and incident response. Removing the limiter or creating an unauthenticated unlock endpoint would weaken protection.

Authentication cannot bypass an unavailable reservation store: operational failures return 503. Throttled responses return 429 with rate metadata and the applicable retry delay. Registration and recovery responses retain their existing generic behavior rather than confirming account existence. New-password provider checks, email dispatch and deployed network paths require their own acceptance; they are not simulated away in a production deployment.

## Durable sessions and password confirmation

| Property | Workspace customer/manager | Platform Owner |
| --- | --- | --- |
| Access JWT | 15 minutes; exact live SID and family required | 15 minutes; exact live SID and family required |
| Idle expiry | 30 minutes | 30 minutes |
| Absolute family cap | 30 days from original creation | 8 hours from original creation |
| Sensitive operation proof | Password verified less than 5 minutes ago | Password verified less than 5 minutes ago |
| Credential binding | HMAC snapshot of account's current salted verifier | SHA-256 fingerprint of account's current salted verifier |
| Confirmation endpoint | `POST /api/auth/reauth/password` | `POST /api/platform/auth/reauth` |
| Security UI | Workspace Settings | Platform Security |

A shorter stored expiry always takes precedence. Refresh, workspace switching, invitation acceptance and password confirmation cannot reset the absolute cap. Password confirmation checks the real password, same-origin request, current exact SID and durable account/tenant authority inside the transaction. It rotates both tokens and immediately invalidates predecessors without ordinary refresh's five-second rotation grace. Concurrent confirmations for the same captured SID have at most one winner. An expired session cannot be revived by password confirmation; sign in again to create a new family.

Workspace background reads, status probes and refresh do not record activity. Its visible-document observer sends throttled hints only for trusted foreground input; successful authorized mutations also record activity. Platform authentication/status/refresh probes do not record activity; ordinary authenticated platform requests retain the established activity behavior. Neither activity path changes password freshness. High-risk workspace permissions are explicitly enumerated in `src/lib/workspace-session-security.ts`; normal print submission and diagnostic permission are not automatically turned into five-minute operations just because they use POST. The UI requires an explicit retry after confirmation; it does not replay a rejected destructive operation.

Fresh login replaces only a presented matching same-principal/same-kind/same-tenant family. Other devices and workspaces remain independent. There is no newly introduced hard account-wide concurrent-session cap; session inventory uses bounded signed pagination, not a 100-session security limit. Users can inspect and revoke their own live families. Workspace revocation checks their password, and platform targets additionally require current same-account platform authority and fresh platform password proof. No workspace role can revoke another account's or an unrelated platform session through that interface.

Production uses audience-specific `__Host-` cookies with Secure, HttpOnly, Path=/ and no Domain. Access cookies are SameSite=Lax; refresh cookies are SameSite=Strict. Browser responses omit bearer and refresh tokens. The explicitly supported desktop HTTP response exception remains behind its established origin/header check; the shipped Tauri UI uses its paired native Agent bridge. Former unprefixed production cookie names are not accepted. All session security endpoints use no-store responses. Duplicate-cookie ambiguity, revocation, kind isolation and stale token reuse remain guarded by `src/lib/session-config.ts` and `src/lib/session-tokens.ts`.

## Migration and stored credentials

`0093_password_only_authentication.sql` removes eight retired factor-only stores and their account/session columns, keeping the immutable earlier migration files and journal entries. Accounts, password hashes, verification state, memberships, role flags, refresh rows, revocation history and all password/idle/absolute timestamps are preserved. A current-verifier fingerprint is added to retained platform policy rows without extending their proof time. This backfill cannot reconstruct a historical password hash that V2 never stored in its policy; review any out-of-band password changes during the upgrade window. It does not create a new password-verification event.

The application is stopped during migration. The production migrator uses one transaction and an advisory lock; unexpected dependencies abort without partially dropping state because there is no cascading drop. The populated-upgrade regression verifies that rollback and preservation, including revoked sessions and idempotent replay. [MIGRATION.md](../MIGRATION.md) contains rollout and rollback steps. Older backups still hold sensitive retired factor material and must retain appropriate custody; the V3 runtime has no reader or activation switch for those mechanisms.

## Monitoring, remaining risk and verification boundary

The Gateway logs failed workspace/manager login and failed/throttled platform login with structured events; manager throttling is logged, and limiter storage errors are separate operational events. Wrong-password confirmation emits `auth.workspace_reauthentication.password_failed` or `auth.platform_reauthentication.password_failed`, containing only the validated request identifier, authenticated user identifier and, for workspace requests, tenant identifier. These events contain no email, password, request body, cookie, token or verifier. A failed warning sink leaves the HTTP 403 denial and reserved retry budget intact; it cannot create fresh proof, rotate credentials or write a successful confirmation audit. Successful logins and password confirmation have the existing audit paths; some login audit writes are best effort and their failures must be monitored. Refresh reuse has its durable audit and existing notification attempt. Source locations are the three login routes, both password-confirmation routes, `src/lib/auth-rate-limit.ts`, `src/lib/log.ts` and `src/lib/session-tokens.ts`.

This repository does not provide a configured unusual-location detector, a complete suspicious-login notification service or an external immutable alert sink. Operators must retain warn/error authentication events in a protected collector, monitor throttling and store failures, test their alert receiver, investigate repeated targeted lockouts and revoke exposed sessions. A log line or best-effort notification is not evidence that a human received an alert. Broad ASVS suspicious-login notification coverage remains unverified.

Password-only login has lower resistance to phishing and stolen passwords than combined authentication. A stolen Platform Owner password can access the cross-tenant control plane; fresh password confirmation does not stop an attacker who also knows that password. Strong unique passwords, password managers, protected mailbox access, deployment access controls and monitored rate limits reduce risk without providing MFA or phishing-resistant authentication. ASVS V6.3.3 remains an explicit unmet requirement/exception for this policy. Removed factor-only mechanisms cannot retain historical PASS results; conditional requirements for absent TOTP or cryptographic challenge ceremonies must be scoped explicitly, while password recovery and mailbox tokens remain in scope. No overall ASVS Level 2 or NIST assurance-level claim is made.

Behavioral evidence is separated from deployment claims: `tests/password-only-auth.integration.test.ts` covers all six workspace roles at both endpoints plus owner authority and platform confirmation; `tests/password-auth-migration.integration.test.ts` covers populated upgrade/rollback; retained session, invitation, reset, cookie and rate-limit suites cover the existing controls. `scripts/acceptance/platform-browser.mjs` and `workspace-browser.mjs` exercise the built UI with local HTTPS and a disposable database. Their result files establish only the environment actually run. Public TLS, real providers, native Windows, Odoo identity policy and physical printer acceptance remain independent release gates.
